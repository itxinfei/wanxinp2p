# 第一部分 现状调研

## 1. 项目概述

### 1.1 背景
心飞金融是一款面向互联网大众的互联网金融平台，提供 **P2P 理财服务** 与 **个人消费信贷服务**，采用**银行存管模式**：用户资金存放于银行存管账户，平台仅发起业务指令，不直接接触资金。

项目由早期教学项目 `wanxinp2p / xinfeip2p` 演进而来。已完成：品牌统一（心飞金融 / xfjr）、包名统一（`com.xfjr.*`）、日志规范化（SLF4J）、密钥外置（Apollo）、RSAUtil 去重、全仓库编译通过。

### 1.2 阶段目标
1. **技术栈升级收尾**：消除"只声明未启用"的中间件（ShardingSphere、Sentinel、Seata 覆盖不足）；
2. **功能完善**：补齐金融合规必备能力（实名认证、逾期/代偿、流标、对账）与运营能力（管理后台、多还款方式、债权转让）。

### 1.3 用户角色

| 角色 | 说明 | 主要场景 |
|------|------|----------|
| 投资人（出借人） | 移动端 `xfjr-front-h5` 用户 | 注册、开户、绑卡、充值、浏览标的、投标、查看收益、提现 |
| 借款人 | 移动端 + 管理后台 | 注册、开户、发标、还款 |
| 平台运营人员 | 管理后台 `xfjr-manager` | 实名审核、标的审核、放款确认、对账差异处理、风控 |
| 系统管理员 | 管理后台 | 用户/角色/菜单权限管理、参数配置 |
| 银行存管系统 | `xfjr-depository`（本地模拟） | 开户、充值、提现、冻结、解冻、放款、还款指令 |

# 第二部分 功能完善需求

> **优先级定义**：P0 = 金融合规/核心链路必备，阻塞上线；P1 = 重要运营能力；P2 = 体验与增强。
> **每条需求包含**：用户故事、功能描述、业务规则/公式、接口设计、数据模型变更、验收标准。

## R-01 实名认证落地（P0）

### 用户故事
作为平台，需要在用户开户/绑卡前完成实名核验，满足合规要求并防范欺诈。

### 现状
- `xfjr-common/.../HttpUtil.getAccessToken(ak,sk)` 已封装百度 AI access_token 获取，**无任何调用方**；
- `IDCardUtil.getInfo()` 仅从身份证号解析生日/性别/年龄，**不校验真实性**。

### 目标与范围
1. 身份证 OCR 识别（正反面 → 姓名、身份证号、地址、有效期）；
2. 二要素/三要素核验（姓名 + 身份证号 [+ 银行卡号]）；
3. 认证状态机与记录留存；认证通过作为开户/绑卡前置条件。

### 接口设计

| 方法 | URL | 说明 |
|------|-----|------|
| POST | `/l/realnames` | 提交实名认证（姓名、身份证号、身份证照片 fileId） |
| GET | `/my/realname` | 查询当前用户实名状态 |
| GET | `/l/realnames/{userNo}` | 内部查询（供开户流程调用） |
| POST | `/l/realnames/{userNo}/reviews` | 人工复核（运营后台） |

请求/响应示例：
````json
// POST /l/realnames
{ "name": "张三", "idNumber": "110101199001011234", "idCardFrontFileId": "F_xxx", "idCardBackFileId": "F_yyy" }
// 200
{ "code": "0", "result": { "userNo": "USR_xxx", "status": "SUCCESS", "channel": "BAIDU_OCR", "certifiedTime": "2026-10-22T10:00:00" } }
````

### 数据模型变更
新建 `p2p_consumer.consumer_realname`：

| 字段 | 类型 | 说明 |
|------|------|------|
| `ID` | bigint | 主键 |
| `CONSUMER_ID` / `USER_NO` | bigint / varchar | 用户 |
| `NAME` / `ID_NUMBER` | varchar | 姓名/身份证号（**加密存储**） |
| `ID_CARD_FRONT_FILE_ID` / `ID_CARD_BACK_FILE_ID` | varchar | 证件照片（引用 R-11 文件服务） |
| `CHANNEL` | varchar | 认证渠道 |
| `STATUS` | varchar | `PENDING / SUCCESS / FAILED` |
| `FAIL_REASON` | varchar | 失败原因 |
| `CREATE_DATE` / `CERTIFIED_DATE` | datetime | 提交/认证时间 |

### 状态机
````text
未认证 --提交--> 认证中(PENDING) --渠道核验通过--> 已认证(SUCCESS)
                        +--核验失败--> 认证失败(FAILED) --重新提交--> 认证中
                        +--OCR不通过/人工介入--> 待复核(REVIEWING)
````

### 配置与安全
- 百度 AK/SK、实名渠道密钥走 Apollo，**禁止硬编码**；
- 身份证号落库加密（RSA/AES），日志脱敏；
- 保留认证渠道原始响应（用于纠纷举证），设置保留期限。

### 验收标准
1. 上传清晰身份证 → OCR 正确识别姓名/身份证号（准确率 ≥ 95%）；
2. 二要素核验失败返回明确错误码（`E_1401xx`）；
3. 未实名用户调用开户/绑卡返回 `未实名` 错误；
4. 认证记录可查询、可追溯，身份证号不明文存储。

## R-02 逾期与代偿处理（P0）

### 用户故事
作为平台，需要自动识别逾期还款、计算罚息并催收；借款人长期逾期时由担保方/平台代偿以保障投资人本息。

### 现状
- 还款服务仅按期收款；`COMPENSATORY`（代偿）/ `COMPENSATORY_REPAYMENT`（代偿还款）枚举已定义但无业务实现；
- `repayment_plan` 无逾期天数字段。

### 业务规则（建议值，需产品最终确认）
1. **逾期判定**：`SHOULD_REPAYMENT_DATE` < 当前日期 且 状态 ≠ 已还；
2. **罚息公式**：
   ````text
   罚息日利率 = 借款人年化利率(BORROWER_ANNUAL_RATE) × 1.5 ÷ 360
   逾期罚息   = 当期应还金额(AMOUNT) × 罚息日利率 × 逾期天数(OVERDUE_DAYS)
   逾期天数   = 实际还款日 - 应还款日（自然日，还款日次日开始计）
   ````text
3. **逾期分级**：M1（1-30 天）、M2（31-60）、M3（61-90）、M3+（>90，进入代偿/催收）；
4. **代偿规则**：逾期 ≥ N 天（建议 90 天）且未还款 → 发起代偿；代偿后债权转移至代偿方。

### 接口设计

| 方法 | URL | 说明 |
|------|-----|------|
| GET | `/l/overdue-repayments?date={date}` | 查询当日逾期计划（分页，支持分片参数） |
| PUT | `/l/repayment-plans/{id}/overdue` | 标记逾期（任务内部调用） |
| POST | `/l/compensatory` | 发起代偿（请求体含还款计划 ID 列表） |
| GET | `/l/compensatory/{no}` | 查询代偿结果 |
| GET | `/my/repayment-plans` | 借款人查看本人还款计划（含逾期） |

### 数据模型变更
`p2p_repayment.repayment_plan` 新增字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `OVERDUE_DAYS` | int | 逾期天数 |
| `OVERDUE_INTEREST` | decimal(18,6) | 逾期罚息 |
| `OVERDUE_LEVEL` | varchar | `M1/M2/M3/M3+` |
| `COMPENSATORY_STATUS` | varchar | 代偿状态 |
| `COMPENSATORY_DATE` | datetime | 代偿时间 |

`REPAYMENT_STATUS` 枚举扩充：`NORMAL / OVERDUE / REPAID / COMPENSATED`。

### 定时任务
新增 `OverdueJob`（`@Scheduled(cron = "0 0 2 * * ?")` + `@SchedulerLock`，每日 02:00，与既有 `RepaymentJob` 错峰）：
1. 扫描 `SHOULD_REPAYMENT_DATE` < 当日 且未还的计划；
2. 计算逾期天数与罚息，标记 `OVERDUE`；
3. 发送短信/站内提醒；
4. 满足代偿条件的推送代偿流程（RocketMQ 异步解耦）。

### 验收标准

## R-10 多还款方式支持（P1）

### 用户故事
借款人需要多种还款方式选择，平台需要正确计算每期本息与平台佣金。

### 现状
仅实现等额本息（`FIXED_REPAYMENT`），其余三种返回 `"-1"`。

### 计算公式

**一次性还款（ALL）**
````text
到期应还 = 本金 × (1 + 年利率 × 月数/12)
````

**先息后本（INTEREST_FIRST）**
````text
每期利息 = 剩余本金 × 年利率/12
末期 = 剩余本金 + 当期利息
````

**等额本息（FIXED_REPAYMENT，已实现）**
````text
月供 = 本金 × 月利率 × (1+月利率)^期数 ÷ [(1+月利率)^期数 - 1]
当期利息 = 剩余本金 × 月利率
当期本金 = 月供 - 当期利息
````

**等额本金（FIXED_CAPITAL）**
````text
每期本金 = 本金 ÷ 期数
当期利息 = 剩余本金 × 月利率
当期应还 = 每期本金 + 当期利息
````

### 实施要点
1. 在 `RepaymentUtil` 中实现四种算法，统一返回 `EqualInterestRepayment`（按期本金/利息/佣金拆分）；
2. `RepaymentServiceImpl.startRepayment` 增加分支处理；
3. 精度统一 `BigDecimal`，`ROUND_HALF_UP`，末项尾差调整（末期轧差，保证本金合计 = 放款金额）；
4. 单元测试覆盖四种方式 + 尾差场景。

### 验收标准
1. 四种还款方式均能生成正确的还款计划与应收计划；
2. 各期本息合计与总还款额一致（尾差已调整）；
3. 平台佣金（利差）按 `COMMISSION_ANNUAL_RATE` 正确拆分。

## 8. 验收标准（Definition of Done）

1. 全仓库 `mvn clean test-compile` 通过（当前已达成）；
2. P0 需求（R-01~R-05）全部交付，含自动化测试（正常 + 异常）；
3. 核心资金链路异常场景可正确回滚，`undo_log` 无残留；
4. 无硬编码密钥、无 `System.out`、无 `printStackTrace`；
5. 管理后台可支撑日常运营，RBAC 生效；
6. 每项变更同步更新 CHANGELOG、JavaDoc、springdoc 接口文档。
