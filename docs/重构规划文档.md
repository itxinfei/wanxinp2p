# 第 1 章 重构背景与动因

## 1.1 为什么重构

项目已完成品牌统一（心飞金融 / xfjr）、包名统一、日志规范化、密钥外置、编译修复，并在技术上完成了主体框架升级（JDK 25 / Spring Boot 4.1.1 / Spring Cloud 2025.1.3 / Spring Authorization Server 1.5.0）。但深度排查发现：**框架是现代的，工程是半成品的**——存在架构级缺陷与大量"声明未启用"的中间件，无法支撑金融平台的合规与可维护要求。

## 1.2 现状问题清单（均有代码证据）

### P0 级（架构缺陷，必须解决）

| 编号 | 问题 | 证据 | 影响 |
|------|------|------|------|
| I-01 | **下游服务零鉴权**：网关把 JWT 拆成 base64 `jsonToken` 走 **query 参数**透传，3 个服务的 `TokenInterceptor` 只解码不校验，`SecurityUtil` 直接信任 | `gateway/filter/AuthFilter.java`、`consumer|repayment|transaction/interceptor/TokenInterceptor.java` | ① 用户信息进 access log / 浏览器历史，泄露；② 服务端口可直达时**可伪造用户身份**直接调用；③ 违反"所有用户输入视为高危"原则 |
| I-02 | **认证中心工程半成品**：约 670 行 JDBC 客户端实现从未启用（7 个类），客户端实际用 InMemory；密钥 `{noop}` 明文；无登出、无令牌黑名单、无 introspection | `uaa/repository/OauthRepositoryJdbc.java`、`uaa/domain/OauthClientDetails(Dto).java` 等 7 个类、`config/AuthorizationServer.java` | 客户端无法管理；密钥泄露即被伪造；JWT 无状态导致**无法踢人下线/封禁**（金融场景必需） |
| I-03 | **银行存管职责错位**：`xfjr-depository` 是"外部银行系统"的模拟，却作为项目内普通微服务存在，与存管代理双向耦合 | `xfjr-depository`（12 实体、3 Controller）、`xfjr-depository-agent-service` | 边界混乱；无法体现"平台不接触资金"的架构约束；存管升级/替换影响平台 |
| I-04 | **分布式事务覆盖不足**：`@GlobalTransactional` 仅 2 处（开户、注册），投标、放款、还款、提现等**全部资金操作未纳入** | `AccountServiceImpl:49`、`ConsumerServiceImpl:77` | 资金不一致风险：钱动了、状态没变 |
| I-05 | **补偿逻辑空壳**：`cancelRegister` 仅打日志，无真实回滚 | `AccountServiceImpl:70`、`ConsumerServiceImpl:170` | 事务失败后数据残留 |

# 第 2 章 重构目标与原则

## 2.1 重构目标

1. **架构清晰**：服务边界按业务域划分，职责单一，依赖单向；
2. **安全达标**：网关统一鉴权 + 服务级独立鉴权，消除下游裸奔与用户信息泄露；
3. **认证完备**：标准 OAuth2 授权中心，客户端可管理、密钥不明文、令牌生命周期完整（签发/校验/刷新/吊销/登出）；
4. **数据有序**：一服务一库，分片可扩展，已设计未使用的表全部启用或明确废弃；
5. **中间件落地**：ES 客户端升级、限流启用、分布式事务全覆盖；
6. **可演进的交付节奏**：分 5 期，每期可独立上线、可回滚。

## 2.2 重构原则

| 原则 | 说明 |
|------|------|
| 绞杀者模式（Strangler Fig） | 新能力并行建设，按域逐步切换，不做大爆炸式重写 |
| 先修安全，后做功能 | I-01/I-02 是安全缺陷，优先于任何功能扩展 |
| 每期可上线、可回滚 | 每期设定准出标准与回滚预案，禁止"憋大招" |
| 标准优先 | 认证用标准 OAuth2/OIDC，不引入私有协议；对外接口签名标准统一 |
| 契约先行 | 服务间通过 `xfjr-api` 契约模块交互，禁跨库直连 |
| 测试护航 | 资金链路必须有异常场景集成测试才能宣称完成 |
| 文档同步 | 代码变更同步更新 CHANGELOG、JavaDoc、springdoc、需求文档 |

## 2.3 非目标（明确不做）

- 不引入 sa-token 替换 Spring Authorization Server（保留标准 OAuth2 能力，理由见专题一 5.1.4）
- 不做持牌化改造（助贷/联合贷模式切换），仅保留架构演进空间
- 不重写前端框架（Vue 3 + Vite / uni-app 已就绪）
- 不替换 RocketMQ / Seata / Apollo / MyBatis-Plus 等已稳定运行的选型

## 3.2 服务划分与职责（现状 → 目标）

| 目标服务 | 职责 | 现状 | 重构动作 |

## 3.4 数据架构

| 规则 | 说明 |
|------|------|
| 一服务一库 | 每个服务只访问自己的数据库（见需求文档 6.1），跨服务数据交互走接口。**待核对**：各服务数据源配置在 Apollo（`micro_service.spring-boot-druid`），本地 `application.yml` 无 JDBC 配置，「一服务一库」现状需读取 Apollo 配置确认，而非假定成立 |
| 分片策略 | 交易库 `p2p_transaction_0/1` 按 `CONSUMER_ID % 2` 分片，贯穿 `project` / `tender` / `claim` |
| 分片实施顺序 | 只读改造 → 灰度双写 → 一致性校验 → 全量切换（见专题四） |
| 敏感数据 | 身份证号/银行卡号/手机号加密存储，展示脱敏 |
| 幂等 | 所有写操作带 `REQUEST_NO` 唯一索引 |
| 归档 | 交易记录留存不少于 5 年；合同与存证不少于证书失效后 5 年 |

## 3.5 认证授权架构（核心）

````text
【令牌签发】uaa-service (Spring Authorization Server)
   ├─ 授权码 + PKCE      → 管理后台 / 移动端（推荐）
   ├─ 密码模式           → 存量前端兼容（已实现，限期整改）
   ├─ 客户端凭证         → 服务间内部调用
   └─ 刷新令牌           → 全模式

【令牌校验】两层，各自独立
   ├─ 网关层：Spring Security Resource Server
   │    校验签名 + 有效期 + 黑名单 → 401 拒绝，不转发
   └─ 服务层：各业务服务 Resource Server
        本地校验 JWT（JWKS 公钥）→ 不依赖任何外部透传参数

【用户上下文】服务内直接读 JWT 声明
   mobile / tenant_id / department_id / user_authorities / payload
   → 废弃 jsonToken query 参数机制（I-01）

【会话治理】
   登出 → Redis 黑名单（jti + 过期时间）
   踢人下线 / 账号封禁 → 黑名单 + 风控联动
   令牌吊销 → /oauth2/revoke
````text

**为什么保留 SAS 而不换 sa-token**：
1. 标准 OAuth2/OIDC 能力（JWKS、introspection、revocation、PKCE、授权码）是等保与对外集成的硬需求，sa-token 的 OAuth2 模块成熟度与生态不及 SAS；
2. 当前架构问题在**工程层**（死代码、明文密钥、下游裸奔），不在框架层，换框架不解决这些问题；
3. sa-token 官方仅声明支持 Spring Boot 3.x / JDK 17，本项目 Spring Boot 4.1.1 + JDK 25 兼容性未经验证，引入风险不可控；
4. 改造工程量（15~24 人天）远大于补全 SAS 工程缺陷（5~8 人天）。

# 第 5 章 关键改造专题

## 5.1 专题一：认证授权体系重构（最高优先级）

### 5.1.1 问题本质

当前是"**网关校验 + 下游信任**"的简化方案：网关校验 JWT 后，把用户信息打包成 base64 放在 `jsonToken` **query 参数**透传，下游 3 个服务的拦截器只解码、不校验。

三个后果：
1. **泄露**：query 参数会进入 Nginx access log、应用日志、浏览器历史；
2. **可伪造**：服务端口可直达时，攻击者自造 `jsonToken` 即可冒充任意用户；
3. **无会话治理**：JWT 无状态，登出/封禁/踢人下线无法生效。

### 5.1.2 方案选型对比

| 方案 | 说明 | 评价 |
|------|------|------|
| A. 现状改良 | `jsonToken` 改 header + 加 HMAC 签名 + 下游验签 | 改动最小，但仍是私有协议，非标准，不推荐 |
| B. **下游独立校验 JWT（选定）** | 各业务服务引入 OAuth2 Resource Server，本地校验 JWT，直接读声明 | 标准、无状态、无透传；资源服务器校验开销低 |
| C. 令牌内省 | 下游统一调 UAA `/introspect` 校验 | 有状态可控（可即时失效），但每次多一次 RPC，UAA 成为瓶颈 |
| D. 换 sa-token | 弃 SAS，用 sa-token 登录态体系 | 失去标准 OAuth2；SB4/JDK25 兼容性未验证；工程量大 |

**选定 B + 黑名单补充**：本地无状态校验保证性能，Redis 黑名单解决"即时失效"需求（登出/封禁场景），兼顾标准与可控。

### 5.1.3 目标方案实施步骤

| 步骤 | 内容 | 涉及 |
|------|------|------|
| S1 | 网关删除 `AuthFilter`（停止 jsonToken 透传） | gateway |
| S2 | 各业务服务引入 `spring-boot-starter-oauth2-resource-server`，配置 JWKS 地址 | 全部业务服务 |
| S3 | 删除 3 个 `TokenInterceptor` 与对应 `WebConfig` 注册 | consumer/repayment/transaction |
| S4 | `SecurityUtil` 改为从 `JwtAuthenticationToken` 读声明 | transaction 等 |
| S5 | UAA 增加 Redis 令牌黑名单（登出/吊销时写入） | uaa |
| S6 | 网关与服务的 JWT 校验增加黑名单查询 | gateway + 各服务 |
| S7 | 新增 `POST /logout` 与 `/oauth2/revoke` | uaa |
| S8 | 客户端改 JDBC + BCrypt，删死代码 | uaa |
| S9 | 前端改用 header 传递令牌（已为 `Authorization: Bearer`，无需改），移除对 `jsonToken` 的依赖（如有） | 前端 |

### 5.1.4 兼容性与回滚

- **兼容期**：S1~S4 可按服务逐个切换，未切换的服务仍走旧机制（保留 `AuthFilter` 但仅对旧路径生效），避免一次性全切；
- **回滚**：任一步骤可通过配置开关回退到旧机制（网关开关控制是否透传 jsonToken）；
- **联调重点**：切换后必须验证"伪造 jsonToken 直连服务返回 401"（FR-130 AC3）。

# 第 6 章 迁移策略与风险控制

## 6.1 总体策略：绞杀者模式（Strangler Fig）

````text
现状系统 ──持续运行──> 逐步替换 ──> 目标架构
   │                        │
   └── 每期独立上线，可回滚 ──┘

原则：
  1. 不做大爆炸式重写，按服务域逐个切换
  2. 每期有明确的准出标准（DoD）与回滚预案
  3. 数据库变更只增不改（加字段/加表），禁直接改语义
  4. 接口契约先行：新接口上线 → 前端切换 → 旧接口标注废弃 → 下架
````text

## 6.2 数据库迁移原则

| 原则 | 说明 |
|------|------|
| 只增不改 | 新字段必须有默认值；禁修改已有字段语义 |
| 双写过渡 | 表结构变更期间双写，校验一致后切读 |
| 脚本化管理 | 所有 DDL/DML 纳入版本化迁移脚本，禁手工改生产库 |
| 回滚脚本 | 每个迁移脚本配套回滚脚本 |
| 存量数据处理 | 见需求文档 DR-08 与下方 DM 清单 |

**存量数据处理清单（DM）**

| 编号 | 迁移项 | 内容 | 风险 |
|------|--------|------|------|
| DM-01 | 启用 RBAC 六表 | 初始化超管角色与菜单；存量账号绑定超管角色 | 中 |
| DM-02 | 启用 `recharge_record` / `withdraw_record` | 从 `depository_record` 与 Redis 回补历史流水 | 中 |
| DM-03 | 启用 `fileobject` | 存量证件图片迁移（如有） | 低 |
| DM-04 | 客户端迁 JDBC + BCrypt | 将 InMemory 客户端配置迁移入库并加密 | 中 |
| DM-05 | `repayment_plan` 增逾期字段 | 存量计划字段默认值回填 | 低 |
| DM-06 | `project_0/1` 增流标字段 | 存量流标数据回填原因与时间（默认"历史数据"） | 低 |
| DM-07 | 新建库 | `p2p_risk`、`p2p_reconciliation`、`p2p_file`、`p2p_message` | 低 |
| DM-08 | ShardingSphere 上线 | 双写 → 校验 → 切换 → 回滚预案 | **高** |

## 6.3 回滚机制

| 层级 | 机制 |
|------|------|
| 代码 | 每期独立分支与 Tag，异常时回滚部署版本 |
| 配置 | Apollo 配置版本化管理，一键回退 |
| 认证 | 网关开关控制是否透传 `jsonToken`（兼容期） |
| 数据 | 每迁移脚本配套回滚脚本；分片阶段可回切单库 |
| 接口 | 旧接口保留一个版本周期，前端可快速切回 |

## 10.1 分支模型

````text
main（线上，受保护）
 └─ test（测试环境）

| feature/* | 从 dev 切出，完成后 MR 回 dev；命名 `feature/<域>-<简述>` |

| 类型 | 用途 |

| `docs:` | 文档 |
| `test:` | 测试 |
| `chore:` | 构建/工具/依赖 |

要求：一次提交一个逻辑变更；提交信息说明"为什么"而不只是"做了什么"；禁提交临时文件、日志、编译产物。
